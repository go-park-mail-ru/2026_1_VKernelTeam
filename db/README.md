# ДЗ 3 — администрирование PostgreSQL

Здесь лежит всё, что относится к настройке БД проекта Клевер:
конфиги сервера, скрипты создания пользователей, миграции и
краткая документация. Собрал в одном каталоге `db/`, чтобы не
размазывать по разным сервисам.

```
db/
├── README.md                       — этот файл
├── config/
│   ├── postgresql.custom.conf      — параметры самого сервера postgres
│   └── pg_hba.conf                 — кто и откуда может подключаться
├── security/
│   ├── 00_init_app_users.sh        — обёртка для запуска SQL с паролями из env
│   └── 01_create_app_users.sql     — создание ролей и выдача прав
├── scripts/
│   └── apply_custom_conf.sh        — подключает наш конфиг к стандартному
├── migrations/                     — копия /migrations, чтобы всё было рядом
└── normalized/                     — описание схемы (не трогал)
```

## 1. Сервисные пользователи

Главное правило: приложение никогда не должно ходить в БД от имени
суперпользователя. Если злоумышленник пробьёт один сервис, не должно
быть так, чтобы он сразу получил доступ ко всей базе.

Поэтому для каждого микросервиса завёл отдельную учётку:

- `auth_app` — работает только с таблицей `user`. Может читать,
  добавлять и обновлять записи. Удалять не может — у нас удаление
  аккаунта реализовано как soft-delete (флаг в той же строке).
- `catalog_app` — полные права на товары, фото, избранное,
  характеристики. К `category` и `user` — только чтение.
- `commerce_app` — полные права на корзину, заказы, чаты, сообщения.
  К товарам — чтение и только одно исключение: может менять колонки
  `status` и `updated_at`, чтобы резервировать товар при покупке.
- `support_app` — только тикеты и сообщения поддержки. К `user` —
  чтение.
- `clover_monitoring` — отдельная учётка для `postgres_exporter`
  и pgbadger. Не видит данные, видит только статистику postgres
  (получает встроенную роль `pg_monitor`).

Над всеми ними висит ещё одна группа — `app_base`. У неё минимум:
право подключиться к базе `clover` и использовать схему `public`.
Сервисные роли её наследуют, чтобы не повторять одни и те же гранты
четыре раза.

Дополнительно у каждой роли стоит `CONNECTION LIMIT` — максимум
параллельных соединений. Это последняя страховка на случай, если
приложение случайно начнёт плодить коннекты в бесконечном цикле.

**Куда положил скрипт и почему именно сюда.** Думал положить
в `migrations/`, но миграции у нас versioned через golang-migrate
и запускаются под суперпользователем — а создание ролей нужно
сделать до того, как приложение вообще стартует. Сервис-специфичный
каталог тоже не подходит: одни и те же таблицы шарят несколько
сервисов. В итоге сложил всё в `db/security/` — рядом с
`db/migrations/`, которые уже там были. Так логичнее: всё про БД
лежит в `db/`.

Скрипт идемпотентный — `DO`-блоки проверяют, есть ли уже такая роль.
Можно перезапустить, ничего не сломается.

## 2. Защита от SQL-инъекций

Используем `pgx` (драйвер pgx/v5 для Go). Он по умолчанию работает
через extended query protocol — это и есть prepared statements:
сам текст SQL сервер парсит отдельно от аргументов, поэтому
подмешать лишний SQL через значения параметра невозможно.

Везде в коде запросы выглядят так:

```go
pool.Query(ctx, "SELECT * FROM product WHERE seller_id = $1", userID)
```

Никаких `fmt.Sprintf` с конкатенацией значений в SQL нет. Проверил
грепом по всему `services/` — пусто.

Есть одно место с динамической сборкой запроса — `UpdateAd` в
`services/catalog/internal/repository/ad/postgres.go` (где `SET`-часть
собирается из тех полей, которые пришли в запросе). Но там собираются
только **имена колонок** из контролируемого `switch` по полям DTO,
а значения по-прежнему уходят через `$N`. Это безопасно.

Дополнительные слои защиты:

- Валидация на уровне DTO — длины строк, форматы, диапазоны
  проверяются до того, как данные попадают в репозиторий.
- `CHECK`-констрейнты в схеме — проверка email regexp, длин,
  рейтингов. На случай, если кто-то решит добавить новый путь
  записи в БД мимо валидации.

## 3. listen_addresses

Стоит `'0.0.0.0'`. На первый взгляд страшно, но в нашей реальности
это не проблема:

- postgres крутится в docker, рядом с микросервисами в одной сети;
- наружу торчит только проброшенный порт (`8010:5432`) — и то только
  на машине разработчика, в проде этого не будет;
- кто реально может подключиться, определяется в `pg_hba.conf`:
  разрешён только диапазон docker-сети, остальные явно reject'нуты.

Вариант `localhost` не подошёл бы — каждый контейнер имеет свой
loopback, и микросервисы из других контейнеров не достучались бы.

## 4. max_connections и connection pool

`max_connections = 150` на сервере. Сумма получилась так:

| Сервис    | Учётка             | CONNECTION LIMIT |
|-----------|--------------------|------------------|
| auth      | auth_app           | 25               |
| catalog   | catalog_app        | 35               |
| commerce  | commerce_app       | 35               |
| support   | support_app        | 15               |
| monitoring| clover_monitoring  | 5                |
| резерв    | postgres, миграции | 35               |
| **итого** |                    | **150**          |

В каждом сервисе настроил pgxpool:

| Сервис    | MaxConns | MinConns |
|-----------|----------|----------|
| auth      | 10       | 2        |
| catalog   | 15       | 3        |
| commerce  | 12       | 3        |
| support   | 6        | 2        |

Логика выбора:

- каждый коннект в postgres — это отдельный процесс, около 10 МБ
  RAM плюс `work_mem` на сложные планы. Делать 500-1000 коннектов
  на 8 ГБ RAM просто бессмысленно;
- если умножить `MaxConns` на типичное число реплик (3-4 для
  тяжёлых сервисов, 2-3 для лёгких), получится примерно 30-60
  коннектов на сервис — суммарно укладывается в 150;
- `MinConns=2-3` держит немного «тёплых» соединений, чтобы первый
  запрос после простоя не дожидался TCP-рукопожатия и SCRAM-аутентификации
  (это ~30-100 мс);
- `MaxConnLifetime=30m`, `MaxConnIdleTime=5m` — соединения
  обновляются, чтобы не накапливать мусор и не страдать от
  забытых NAT-сессий.

Если когда-нибудь сервисов станет много (8+ реплик на сервис),
поставлю pgbouncer в режиме transaction pooling. Пока с этим
справляется сам pgxpool.

## 5. Таймауты

| Параметр                             | Значение  |
|--------------------------------------|-----------|
| statement_timeout                    | 30 секунд |
| lock_timeout                         | 5 секунд  |
| idle_in_transaction_session_timeout  | 60 секунд |
| idle_session_timeout                 | 0 (выкл.) |

Почему именно так:

**statement_timeout = 30s.** В нашей нагрузке (маркетплейс, OLTP)
обычный запрос идёт сотни миллисекунд. Если что-то висит дольше
30 секунд — это либо плохой план запроса, либо deadlock, либо
кто-то прислал намеренно тяжёлый запрос на поиск. Минута — уже
плохо: пока запрос висит, у нас занят и worker сервиса, и слот
в пуле. 5 секунд было бы слишком жёстко — иногда легально нужны
тяжёлые отчёты. 30 — нормальный компромисс.

С точки зрения защиты от DoS: если кто-то начнёт долбить тяжёлый
endpoint, через 30 секунд его запросы будут принудительно убиваться
и пул освобождаться.

**lock_timeout = 5s.** В OLTP-приложении блокировки не должны
висеть. Если запрос ждёт лок 5 секунд — что-то пошло не так, лучше
вернуть пользователю ошибку и предложить повторить, чем держать
его (и worker) дальше.

**idle_in_transaction_session_timeout = 60s.** Защита от ситуации
«разработчик начал транзакцию и забыл commit». Такая транзакция
держит блокировки и мешает autovacuum. Минута — щедрый порог.

Таймауты задаются в трёх местах одновременно:

1. На сервере (`postgresql.custom.conf`) — дефолт для всех;
2. В DSN сервиса (`options=-c statement_timeout=...`);
3. В клиенте pgx через `RuntimeParams` — pgx делает `SET` перед
   тем, как отдать соединение в пул.

Тройная подстраховка нужна потому, что есть разные пути в коде
(не все идут через pgxpool), и один путь может обойти один из
механизмов.

## 6. Логи и pgbadger

pgbadger — это утилита, которая читает логи postgres и делает из
них HTML-отчёт с топом медленных запросов, графиками, статистикой.
Чтобы он мог разобрать наши логи, формат должен быть строго
определённым.

В `postgresql.custom.conf` стоит:

```
log_destination          = 'stderr,csvlog'
logging_collector        = on
log_directory            = '/var/log/postgresql'
log_filename             = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_rotation_age         = '1d'
log_rotation_size        = '100MB'

log_line_prefix          = '%t [%p]: user=%u,db=%d,app=%a,client=%h '
log_min_duration_statement = '500ms'
log_checkpoints          = on
log_connections          = on
log_disconnections       = on
log_lock_waits           = on
log_temp_files           = 0
log_autovacuum_min_duration = '1s'
log_timezone             = 'UTC'
```

В `docker-compose.yaml` поднял контейнер `pgbadger`. Раз в 5 минут
он перечитывает свежие CSV-логи (флаг `-I` — incremental, помнит,
что уже было обработано) и складывает HTML в volume `pgbadger_reports`.

**Порог медленных запросов = 500 мс.** Это меньше, чем
`statement_timeout`, и достаточно, чтобы поймать всё реально
проблемное. Лента товаров и логин должны укладываться в 100-200 мс,
оформление заказа — в 300 мс. Если запрос пересёк 500 мс, это уже
кандидат на оптимизацию и надо смотреть план. На стенде это не
заваливает диск логами, потому что нормальные запросы туда просто
не попадают.

## 7. pg_stat_statements

Это встроенное расширение, которое копит статистику по запросам:
сколько раз вызывался каждый шаблон запроса, сколько суммарно
потратил времени, сколько прочитал блоков. Шаблон — это запрос с
подменёнными `$1, $2, ...`, то есть статистика агрегируется по
форме запроса, а не по конкретным значениям.

Чтобы расширение работало, оно должно быть пред-загружено в postgres
при старте, поэтому в конфиге стоит:

```
shared_preload_libraries = 'pg_stat_statements,auto_explain'
pg_stat_statements.max  = 10000
pg_stat_statements.track = all
pg_stat_statements.save  = on
```

Само расширение активируется миграцией
`000019_enable_pg_stat_statements.up.sql` (`CREATE EXTENSION`).

Право читать `pg_stat_statements` выдано только мониторингу.
Сервисным учёткам это не нужно — и не должно быть видно, потому
что чужие запросы могут косвенно содержать чувствительные данные
(имена таблиц, фильтры).

## 8. auto_explain

Тоже встроенное расширение. Если запрос превысил порог по времени,
auto_explain автоматически кладёт его план в лог — не нужно потом
вручную ловить и переигрывать запрос с `EXPLAIN ANALYZE`. План
уже есть, с реальными таймингами.

```
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze      = on   # реальное время, не estimated cost
auto_explain.log_buffers      = on   # сколько блоков читалось
auto_explain.log_wal          = on   # нагрузка на WAL
auto_explain.log_format       = text # нормально читается глазами и pgbadger
auto_explain.sample_rate      = 1.0  # 100% медленных запросов
```

На стенде включил выборку 100%. Если когда-нибудь объём логов на
проде станет проблемой, можно сделать `sample_rate = 0.1` — будет
логироваться каждый десятый медленный запрос.

## 9. Мониторинг

В compose уже был prometheus + grafana (это с прошлого ДЗ). Сюда
добавил:

- **postgres_exporter** — экспортит метрики postgres в prometheus:
  число активных коннектов, commits/rollbacks, hit-ratio буферов,
  locks, размер WAL. Подключается под учёткой `clover_monitoring`.
- **pgbadger** — генерит HTML-отчёт по логам.

Алерты в `deployments/prometheus/alerts.yml` уже были (из коммита
с monitoring infrastructure). Графана дашборды подхватывает
автоматически из `deployments/grafana/dashboards/`.

## 10. Что менять при переезде в прод

Локальная конфигурация и продовая — всё-таки разные вещи. Что
точно стоит поменять:

- Все пароли (`*_DB_PASSWORD`) переезжают в Vault или k8s Secrets.
  В `.env` остаются только имена секретов, реальные значения
  подхватываются на старте пода.
- `ssl = on` плюс сертификаты. `pg_hba.conf` переключить на
  `hostssl` — отказать в незашифрованных соединениях.
- `max_connections` пересчитать под реальное число реплик k8s.
- `auto_explain.sample_rate` опустить до 0.1, если объёмы логов
  начнут давить на диск.
- При росте числа реплик — поставить pgbouncer.
